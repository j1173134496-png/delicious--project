## 3. 目标与范围

### 3.1 目标

从空目录实现一个可运行、可演示、可继续扩展的原生微信小程序 MVP，覆盖 PRD 的核心用户路径：

1. 打开小程序后可以在四个 Tab 间导航。
2. 用户可以查看和编辑个人信息、生成/输入邀请码并在本地完成情侣绑定演示，查看纪念日天数。
3. 用户可以和八条进行本地 mock 对话，进行喂食和抚摸，看到等级、经验、饱食度和心情变化；检测到倾诉文本时生成不泄露原文的情绪关怀提醒。
4. 用户可以浏览未解锁、已解锁、甜品区菜谱，添加/编辑菜品、上传本地图片、评分和备注。
5. 用户可以按月份浏览照片，上传照片和描述，进入大图预览并删除自己上传的照片。
6. 所有文字数据通过 Service 层写入本地 Storage，图片通过小程序文件系统保存；模块之间使用统一的数据模型和状态接口。
7. 在没有真实 LLM、云数据库和图片素材的情况下，仍能通过 mock 数据和占位图完成演示，并明确记录这些边界。

### 3.2 本轮边界与假设

- 以 PRD v1.0 为需求基线，默认实现 Phase 1～4 的可演示核心路径，并完成 Phase 5 中的必要样式和边界处理。
- LLM、情绪识别和主动提醒均使用本地 mock；保留后续 API 替换接口，不读取或提交任何真实密钥。
- 数据为单设备本地数据；邀请码绑定在 MVP 中模拟双用户流程，不能实现跨设备同步。
- PRD 未给出猫咪素材和完整菜谱清单，使用 CSS/Emoji/内置占位图与 PRD 中的示例菜谱，资源接口保持可替换。
- 未提供真实纪念日，默认用当前日期或可编辑字段初始化，并在界面标明可修改。
- 优先保持原生 WXML/WXSS/JS，无强制引入需要额外构建的第三方包；若实现 MobX 需要依赖，则必须同时提供可导入配置或记录依赖限制，不能让核心页面因依赖缺失无法运行。

## 6. 风险与阻塞条件

### 风险及应对

1. **微信开发者工具不可用**：只能完成 JSON/JS/路径静态检查；必须在执行日志中标记运行时未验证，不能将静态检查表述为完整通过。
2. **缺少猫咪图片和图标**：采用 CSS/Emoji/占位资源；把真实资源目录和状态名固定为接口，后续替换不改页面逻辑。
3. **本地模式无法真正同步情侣双方**：只实现本地模拟绑定；Service 接口保留 `coupleId` 和同步边界，并在 README/日志中说明限制。
4. **Storage 与本地文件生命周期差异**：所有图片元数据和文件操作集中在 Service，删除、失效路径和清除缓存必须有降级处理。
5. **PRD 待讨论事项未决**：默认菜谱、LLM 供应商和纪念日采用可编辑默认值；不阻塞 MVP，但记录为后续产品决策。
6. **无包管理配置**：优先使用原生实现；若引入依赖，必须同时提供安装/构建说明和不依赖该包的降级策略。

### 必须暂停并报告的条件

- 计划文件被删除、无法读取或与实际仓库状态明显不符。
- 无法创建小程序骨架且没有可行的本地替代方案。
- 关键 Service/页面实现依赖用户未提供的外部凭据或不可逆外部操作。
- 任一任务验证发现会阻止后续任务的结构性错误，且 Executor 无法在当前工作区修复。
- 需要改变 PRD 核心行为或扩大范围时，先暂停并向主 Agent/用户报告，不自行假设。
